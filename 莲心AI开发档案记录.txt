第一章  项目概述
1.1  项目简介
莲心AI 是一个运行在 Windows 桌面端的个人AI助手，基于 PyQt5 图形界面，使用 DeepSeek API（OpenAI 兼容）作为语言模型后端，支持文字对话、语音交互、工具调用、桌面自动化等功能。
项目路径：E:\Desktop\莲心AI\
主入口文件：main.py（GUI版）、main_cli.py（命令行测试版）
1.2  技术栈
语言模型：DeepSeek API（deepseek-chat），通过 openai SDK 调用（OpenAI 兼容接口）
GUI 框架：PyQt5，含自定义控件和动画状态机
语音识别（STT）：faster-whisper（本地离线，base模型，CPU int8）+ 阿里云NLS（实时流式，待机模式）
语音合成（TTS）：Edge-TTS（zh-CN-XiaoxiaoNeural 小晓声）+ pygame 播放
数据持久化：SQLite（对话历史）+ JSON（配置/记忆/待办/闹钟）
运行环境：Windows 10，Python 3.12
1.3  用户数据目录
所有持久化数据统一存储在 C:\Users\<用户名>\.lianxin\ 目录下，与项目代码分离：
user_config.json        —  DeepSeek API Key、模型配置、阿里云STT配置
long_term.json          —  AI 长期记忆（facts 数组）
alarms.json             —  闹钟列表
todo.json               —  待办事项列表
proactive_settings.json —  主动聊天调度配置
accompany_stats.json    —  陪伴统计数据
utils/paths.py 的 get_user_data_dir() 统一返回该目录，首次运行时自动创建。
启动时 migrate_legacy_files() 会将旧位置（项目内 data/、memory/）的配置文件自动迁移到新目录。
注意：对话历史 SQLite 数据库（memory/conversations.db）目前仍在项目目录内，尚未迁移。

第三章  AI 大脑（brain/agent.py）
3.1  AgentCore 类概述
AgentCore 是莲心的核心大脑，封装了 DeepSeek API 调用、Function Calling 循环、对话历史内存管理和 SQLite 持久化。
使用 openai.OpenAI 客户端，通过 base_url='https://api.deepseek.com' 连接 DeepSeek（完全兼容 OpenAI 接口）。
3.2  初始化流程
agent = AgentCore()
实例化时依次执行：
1. 调用 get_api_config() 读取 user_config.json 中的 DeepSeek 配置
2. 实例化 openai.OpenAI(api_key=..., base_url=...)
3. 实例化 HistoryManager，从 SQLite 恢复上次会话历史
4. 调用 _build_system_prompt_once() 构建完整 System Prompt，整个运行期间不变
3.3  System Prompt 结构（_build_system_prompt_once）
System Prompt 由以下部分组成：
基础人格设定（get_base_prompt()，来自 config.py 的 _BASE_PROMPT）
启动时间信息块：公历+时分秒+星期+农历（zhdate库）+节假日（chinese_calendar库）
长期记忆块：从 long_term.json 读取的 facts 列表，格式：- 事实1\n- 事实2...
注意：时间信息是启动时的值，如需实时时间应调用 get_current_time 工具。
3.4  chat() 主接口
response = agent.chat(user_message, on_tool_call=None, on_tool_result=None)
参数说明：
user_message       —  用户输入的文字字符串
on_tool_call(name, args)   —  工具被调用时的回调（可选，GUI用来显示状态）
on_tool_result(name, result) —  工具执行完毕的回调（可选）
执行流程：
1. 将用户消息追加到内存历史列表 self.history
2. 如是本会话第一条消息，用前20字更新 SQLite 会话标题
3. 将用户消息写入 SQLite（history_manager.save_message）
4. 调用 _function_calling_loop() 执行完整 Function Calling 循环
5. 将 AI 回复追加到内存历史列表和 SQLite
6. 返回 AI 回复文本字符串
3.5  Function Calling 循环（_function_calling_loop）
最多循环 10 次防止无限调用，每轮：
构建 messages = [{role:system, content:system_prompt}] + self.history
调用 client.chat.completions.create(model, max_tokens, tools=TOOL_DEFINITIONS, tool_choice='auto', messages, timeout=30)
finish_reason == 'stop'    → 返回 choice.message.content
finish_reason == 'tool_calls' → 遍历每个 tool_call：
  解析 function.name 和 JSON.loads(function.arguments)
  执行 execute_tool(name, args) 得到结果字符串
  以 role='tool', tool_call_id=... 追加结果，继续循环
其他 finish_reason → 返回错误提示
3.6  其他公开接口
agent.clear_history()         —  清空内存历史（SQLite保留）
agent.new_session()           —  开启新会话（内存清空 + SQLite新建session）
agent.get_history_manager()  —  返回 HistoryManager 实例（供历史对话框使用）
agent.get_history_summary()  —  返回当前会话轮数文本


第四章  工具系统（brain/tools.py）
4.1  结构说明
tools.py 包含两部分：
TOOL_DEFINITIONS：发送给 DeepSeek API 的工具描述列表（OpenAI Function Calling 格式的 JSON 列表）
Python 执行函数：与每个工具同名的函数，由 execute_tool(name, args) 路由调用，统一返回字符串
execute_tool 通过 name → function 的字典映射调用对应函数，所有工具的返回值都是字符串（DeepSeek 接收 role='tool' 的消息）。
4.2  完整工具清单
4.2.1  文件读取类
read_file(path)
  读取文件第0块（开头15000字符）。支持 .txt/.md/.py/.csv/.json 等文本（自动检测编码 chardet+回退）、.docx Word文档（python-docx）、.pdf PDF（pdfplumber）。文件较长时返回注明总块数，提示调用 read_file_chunk。
read_file_chunk(path, chunk_index)
  读取文件的指定分块（每块15000字符），用于长文件分段阅读。chunk_index 从0开始。
list_directory(path='')
  列出目录内容（子目录+文件名+文件大小）。不传参数默认列桌面（Path.home()/Desktop）。
search_files(directory, keyword)
  在目录中递归搜索包含关键词的文件名（rglob），最多返回50条匹配路径。
read_excel(file_path, sheet_name=None, max_rows=100)
  读取 .xlsx Excel文件，以 Markdown 表格格式返回，默认最多100行。依赖 openpyxl 库。
4.2.2  文件写入类
write_file(path, content)
  将文本内容写入文件（UTF-8编码），自动创建父目录。
write_docx(file_path, content)
  将文本写入 .docx Word文档，按双换行符分段。依赖 python-docx。
format_document(content, output_path, use_template=True)
  将 Markdown 格式内容转换为格式优美的 Word 文档，推荐用于生成报告。依赖 python-docx。
write_excel(file_path, data, sheet_name='Sheet1')
  将二维数组写入 .xlsx 文件（可创建新文件或覆盖）。依赖 openpyxl。
copy_excel_content(source_path, target_path, source_sheet=None, target_sheet=None)
  将源 Excel 文件的内容复制到目标 Excel 文件（支持指定工作表）。
4.2.3  系统操作类
open_app(name)
  打开应用程序/文件夹/文件。支持中文别名（记事本→notepad、计算器→calc、画图→mspaint、资源管理器→explorer、桌面→Desktop路径、命令行→cmd、任务管理器→taskmgr、控制面板→control、截图工具→snippingtool），也支持完整路径。查找顺序：①系统别名 → ②用户快捷启动列表 → ③os.startfile → ④PATH搜索 → ⑤_KNOWN_PATHS（非递归）→ ⑥shell回退。已完全去除 glob.iglob 递归搜索，避免 GIL 竞争导致 UI 白屏。
run_command(command)
  执行 shell 命令（白名单限制，超时15秒）。白名单：dir/ls/echo/type/cat/python/pip/where/whoami/cd/pwd/hostname/ipconfig/del/rm/rd/rmdir/mkdir/New-Item。
get_clipboard()
  通过 PowerShell Get-Clipboard 读取剪贴板文字内容（最多3000字符，无需额外依赖）。
run_python_code(code, timeout=10)
  在安全沙箱子进程中执行 Python 代码。沙箱限制：禁用 open/exec/eval/__import__/globals/locals/vars/dir/help/input/breakpoint 等危险内置函数，仅保留安全的计算类函数。
4.2.4  信息查询类
get_current_time(format='full')
  获取当前时间/日期/星期/农历/节假日。format 可选：full（完整）/date（仅日期）/time（仅时间）/weekday（仅星期）/lunar（仅农历，需 zhdate 库）/holiday（仅节假日，需 chinese_calendar 库）。
get_balance()
  通过 utils/balance.py 调用 DeepSeek 官方接口，实时查询账户余额并格式化返回。
4.2.5  联网类
web_search(query, max_results=5)
  使用 DuckDuckGo 搜索引擎（duckduckgo-search 库）联网搜索，返回标题+链接+摘要，最多10条。
fetch_webpage(url, max_length=3000)
  HTTP GET 获取网页，用 BeautifulSoup+lxml 提取纯文本，模拟 Chrome UA，超时15秒。遇到 403 反爬时返回错误提示，建议改用 fetch_webpage_via_api。
fetch_webpage_browser(url, max_length=3000)
  使用浏览器内核（Playwright/Selenium）获取网页，可绕过反爬措施，速度较慢。
fetch_webpage_via_api(url, max_length=3000)
  通过 r.jina.ai 解析服务获取网页 Markdown 格式内容，适合知乎/百度百科等严格反爬网站，超时60秒，含2次重试机制（urllib3.Retry）。
网页访问策略（System Prompt 中规定）：优先 fetch_webpage → 失败改 fetch_webpage_via_api → 再失败改 fetch_webpage_browser。
4.2.6  记忆与任务类
save_memory(fact)
  将一句话事实追加写入 ~/.lianxin/long_term.json 的 facts 列表，重复检测。下次启动时注入 System Prompt，AI 永久记得。
add_todo(title, due_time=None, priority='medium', description='')
  添加待办事项。due_time 为 ISO 格式字符串（如 2026-04-21T15:00:00）或 null。priority 为 high/medium/low。持久化到 ~/.lianxin/todo.json。
list_todos()

4.3  文件内容提取实现细节
.docx 提取：python-docx 遍历 body 中的段落（p 标签）和表格（tbl 标签），保持原文档顺序
.pdf  提取：pdfplumber 逐页提取，标注页码，无长度限制
文本文件：读取原始字节，优先 chardet 检测编码（置信度>=0.6），回退 utf-8/gbk/gb2312/gb18030/latin-1
分块逻辑：_CHUNK_SIZE=15000字符，超长文件自动分块，首块用 read_file，后续块用 read_file_chunk(path, chunk_index)

6.1  agent_worker.py  AI 对话线程

worker.error_occurred.connect(on_error)
worker.start()
信号：response_ready(str) / tool_called(str) / error_occurred(str)
run() 中调用 agent.chat(message, on_tool_call=lambda name,args: self.tool_called.emit(name))，完成后发射 response_ready。
6.2  voice_worker.py  语音识别线程
分两个类：
ModelLoader(listener)   —  仅加载 Whisper 模型（首次约需5~15秒），信号 finished()
VoiceWorker(listener)   —  调用 listener.record() 录音 + listener.transcribe() 识别
VoiceWorker 信号：transcription_ready(str) / error_occurred(str)
6.3  speaker_worker.py  TTS 播放线程
worker = SpeakerWorker(speaker, text)
worker.speak_started.connect(...)
worker.speak_finished.connect(...)
run() 调用 speaker.speak(text)，阻塞直到播放完毕，前后发射 speak_started / speak_finished 信号。
speak_started 信号触发：动画切换到 talking 状态（trigger_event('speak_start')）。
speak_finished 信号触发：动画切换回 idle 状态（trigger_event('speak_end')）。
6.4  standby_worker.py  待机监听线程
worker = StandbyWorker(listener)
worker.wake_detected.connect(on_wake)
循环执行：record(silence_threshold=0.02, silence_seconds=1.0, max_seconds=6.0) → transcribe → 判断唤醒词。
唤醒词列表（含谐音变体）：莲心在吗/连心在吗/莲心莲心/莲心/你好/您好/泥好 等。
结束语列表：回答结束/回答完毕/就这些/发送/提交 等。
主窗口收到 wake_detected 后切换到待机对话模式；检测到结束语时截取内容提交给 AgentWorker。
工具函数 contains_wake_word() / contains_end_phrase() / strip_end_phrase() 可单独导入使用。
6.5  proactive_worker.py  主动聊天生成线程
worker = ProactiveWorker(history_manager)
worker.response_ready.connect(on_proactive_msg)
run() 中构建上下文：最近1个会话的最后12条消息 + 长期记忆（最多20条）。
独立调用 DeepSeek API（不使用 AgentCore），System Prompt 风格不同：温柔毒舌，主动发消息，1~3句话，max_tokens=256。
6.6  listening_worker.py  单次录音线程

run() 调用 brain.vision.describe_image(image_path)，完成后发射 finished，失败发射 error。在 main_window.py 末尾定义，轻量线程，仅封装单张图片的 API 调用。
信号：finished(str) / error(str)
worker.finished.connect(lambda desc: ...)   /   worker.error.connect(lambda err: ...)

第七章  语音模块（voice/）
7.1  listener.py  VoiceListener（STT）
封装麦克风录音 + 静音检测（VAD）+ faster-whisper 语音识别。
关键参数：SAMPLE_RATE=16000Hz，CHUNK_SIZE=1024，model_size='base'，language='zh'，device='cpu'，compute_type='int8'
record() 录音算法：
sounddevice.InputStream 采集 float32 单声道16kHz音频
每块1024采样，计算 RMS = sqrt(mean(chunk^2))
RMS > silence_threshold（默认0.015）则视为有声音，开始录制
连续静音帧超过 silence_seconds（默认1.5s）对应帧数则停止
最长 max_seconds（默认30s），防止无限录音
返回 float32 numpy 数组（可直接传给 WhisperModel.transcribe）
transcribe(audio) → str：调用 WhisperModel.transcribe()，合并所有 segment 文本。
load_model()：懒加载 faster-whisper WhisperModel（首次约5~15秒），之后缓存在 self._model。
stop()：设置 _stop_flag，中断正在进行的录音循环。
7.2  speaker.py  VoiceSpeaker（TTS）
使用 Edge-TTS 合成语音 + pygame.mixer 播放，默认音色：zh-CN-XiaoxiaoNeural。
speak(text) 流程：
调用 asyncio.run(edge_tts.Communicate(text, voice=self._voice).save(tmp_path)) 生成 MP3 临时文件
pygame.mixer.music.load(tmp_path) + .play() 播放，轮询等待播放完毕
播放完毕后删除临时文件
stop()：self._stop_flag = True + pygame.mixer.music.stop()，立即打断当前播放。
init_player()：初始化 pygame.init() + pygame.mixer.init()，调用一次即可。
7.3  aliyun_stt.py  阿里云实时语音识别
用于待机模式的持续监听，通过阿里云NLS SDK（WebSocket协议）进行实时流式语音识别，延迟更低。
配置来源：user_config.json 的 aliyun_stt 节点（access_key_id / access_key_secret / app_key）。
SDK 已内置在项目目录 alibabacloud-nls-python-sdk/ 中，需本地安装：cd alibabacloud-nls-python-sdk && pip install -e .

第九章  辅助功能模块
9.1  主动聊天调度（utils/proactive_chat.py）
ProactiveChatScheduler 管理莲心主动发起对话的时机，每5分钟由主窗口 QTimer 轮询。
should_fire() 判断逻辑（按顺序短路）：
1. enabled == False → False
2. 用户最近活跃（defer_until 未到期）→ False
3. 距上次主动消息 < min_interval_minutes（默认25分钟）→ False
4. 当前小时权重 weights[hour] <= 0 → False
5. 概率公式：P = (weight/10) * (frequency/30) * 0.08 * 1.5，上限 0.3
notify_user_active()：用户发消息时调用，将主动聊天推迟 user_defer_minutes 分钟。
notify_fired()：主动消息发出后调用，记录 _last_fire_time。
debug_fire()：调试模式，忽略所有限制直接触发。
9.2  开机自启（utils/autostart.py）
通过修改 Windows 注册表实现开机自启：
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
键名：莲心AI
值：python.exe main.py --autostart（或打包后的 exe 路径）
main.py 支持 --autostart 启动参数，自启时最小化到任务栏，不弹窗打扰用户。
check_network()：检查网络连接是否可用（启动时调用）。
9.3  番茄钟（gui/pomodoro_dialog.py + utils/pomodoro_stats.py）
经典番茄工作法：25分钟专注工作 + 5分钟短休息，每4个番茄后长休息15分钟。统计今日完成番茄数，持久化到 pomodoro_stats.json。
9.4  陪伴统计（utils/accompany_stats.py + gui/accompany_dialog.py）
记录与莲心对话的累计时长（今日/总计），持久化到 accompany_stats.json。
9.5  余额查询（utils/balance.py）
get_balance_info() 调用 DeepSeek 官方 API 查询账户余额，format_balance_message() 格式化为可读文本，由 get_balance 工具调用。

第十一章  接手开发指南
11.1  快速了解项目建议阅读顺序
1. config.py           —  了解 API 配置结构和人格设定的完整内容
2. brain/agent.py      —  了解对话主循环和 Function Calling 流程
3. brain/tools.py      —  了解所有工具的定义和 Python 实现
4. gui/main_window.py  —  了解 GUI 整体结构和信号槽连接关系
5. workers/*.py        —  了解各后台线程的信号接口
6. utils/ 各文件       —  了解各业务数据结构
11.2  如何添加新工具
三步操作，全部在 brain/tools.py 中完成：
步骤1：在 TOOL_DEFINITIONS 列表末尾添加工具 JSON 描述（含 type/function/name/description/parameters）
步骤2：实现对应 Python 函数（函数名必须与工具名一致），返回字符串
步骤3：在文件末尾的 execute_tool(name, args) 路由字典中添加 name → 函数 的映射
然后在 config.py 的 _BASE_PROMPT 中添加该工具的使用时机说明，让 AI 知道何时调用。
11.3  如何修改人格设定
直接修改 config.py 中的 _BASE_PROMPT 字符串。重启程序后生效（AgentCore.__init__ 重新构建 System Prompt）。
如需运行时热重载，需修改 AgentCore._function_calling_loop() 每次从 config 重读（有性能开销）。
11.4  如何添加新 GUI 对话框

第十四章  QQ聊天功能
14.1  功能概述
莲心AI 通过接入 NapCatQQ 实现了 QQ 聊天功能。NapCatQQ 是一款基于 QQ NT 内核的 Shell 注入工具，它劫持 QQ NT 进程并向外暴露 OneBot v11 协议的 WebSocket 接口，使得莲心可以收发 QQ 消息并实时响应。
本功能使得莲心具备以下 QQ 对话能力：
私聊自动回复：任何用户发来的私聊消息均会触发回复
群聊 @ 回复：仅在用户 @ 机器人时触发回复，并自动 @ 发送者
多会话隔离：每个用户的私聊和群聊均拥有独立的 AgentCore 对话历史
记忆共享：所有 QQ 会话共享 long_term.json 记忆文件，与桌面版读写同一份长期记忆
14.2  技术架构
QQ 聊天功能的整体架构如下：
QQ 手机端 ←→ NapCatQQ（管理员窗口）── WebSocket ──→ QQBridgeWorker ──→ AgentCore（每用户独立实例）
                              端口 3001                workers/qq_bridge_worker.py
数据流说明：
NapCatQQ 作为 Shell 层注入 QQ NT 进程，劫持消息收发
NapCatQQ 在本地 127.0.0.1:3001 开放 WebSocket 服务器（OneBot v11 协议）
莲心端的 QQBridgeWorker（QThread 子线程）通过 WebSocket 客户端连接 NapCatQQ
QQBridgeWorker 接收消息后，提取文本并路由到对应会话的 AgentCore.chat() 方法
AgentCore 调用 DeepSeek API 生成回复，QQBridgeWorker 通过 OneBot API 将回复发回 NapCatQQ
NapCatQQ 将回复注入 QQ NT 进程，发送到对应的 QQ 好友或群聊
会话隔离策略：
私聊会话 key：qq_private_{user_id}
群聊会话 key：qq_group_{group_id}_{user_id}
每个 key 对应一个独立的 AgentCore 实例，拥有独立的短期对话历史
所有 AgentCore 实例共享同一个长期记忆（long_term.json）

实现要点：

14.7  对话策略
QQ 桥接的对话策略如下：
私聊回复：收到任何私聊消息均回复（忽略机器人自己的消息）
群聊回复：仅在消息中包含 @机器人 时回复，并自动在回复中 @ 原发送者
会话隔离：私聊和群聊分别以不同 key 隔离，每个会话拥有独立的 AgentCore 实例和对话历史
长期记忆共享：所有 QQ 会话的 long_term.json 与桌面版共享，同一份记忆文件
自我消息过滤：忽略 QQ 号为机器人自身的消息，避免自回复循环
14.8  风控防护
为降低 QQ 账号被封禁的风险，实现了多层风控防护机制。以下机制在 workers/qq_bridge_worker.py 中实现：
（1）消息限速
同一会话每 4 秒最多回复 1 条消息。消息频率超过限制时自动忽略，并在日志中记录（限速前 3 次打印警告，之后静默）。
MIN_REPLY_INTERVAL = 4.0   # 同一会话最小回复间隔（秒）
（2）模拟打字延迟
在收到消息后、发送回复前，随机等待 3~8 秒模拟人类打字速度，避免瞬时回复特征。连续发送失败时延迟加倍（最多 4 倍），降低被行为分析检测到的概率。
TYPING_DELAY_MIN = 3.0   # 最短等待秒数
TYPING_DELAY_MAX = 8.0   # 最长等待秒数
（3）每日回复上限
每天最多回复 120 条消息，跨日自动重置计数。达到上限后当天不再回复，避免过度活跃。
DAILY_REPLY_LIMIT = 120  # 每日回复上限
（4）深夜静默机制
凌晨 1:00 至 7:00 为静默时段，默认不回复任何消息。但设计了暗号唤醒机制：
暗号"醒醒"：将机器人从静默中唤醒，之后正常回复
暗号"晚安好梦"：让机器人继续静默
白天天亮后自动退出静默状态
SILENT_HOUR_START = 1  # 凌晨静默开始（1:00）
SILENT_HOUR_END   = 7  # 凌晨静默结束（7:00）
（5）失败退避
连续发送消息失败时，发送延迟会根据连续失败次数逐步加倍（最多 4 倍），并在日志记录连续失败次数。
（6）可中断休眠
所有等待延迟以 0.5 秒为粒度循环检查 _running 标志，确保 stop() 方法可以快速中断休眠，避免退出时卡死。

双进程依存：NapCatQQ（管理员窗口）和莲心 AI 必须同时运行，QQ 聊天功能才能正常使用
环境依赖：莲心需在 conda lianxin 环境中运行，并已安装 websocket-client 包
账号安全：莲心小号为 3786508452（莲心），用户大号为 2648025746（雨心）。建议使用小号测试
网络要求：NapCatQQ 需要联网（QQ 登录需要网络），莲心需要联网调用 DeepSeek API

12.15  技能系统（2026-05-14）
莲心 AI 新增技能系统（Skills System），借鉴 EchoBot 的按需加载模式。技能包是存储在 skills/ 目录下的独立知识/工具包，可按需激活，无需将所有工具全量加载到 system prompt。
核心机制：
brain/skill_manager.py — 技能发现、激活/停用、动态工具合并、知识注入
skills/ 目录 — 每个子目录为一个技能包，含 SKILL.md（元数据+知识）和可选 tools.py（自定义工具）
SKILL.md 格式：YAML 前置元数据（name/description/version）+ Markdown 正文（激活后注入 system prompt）
激活机制：LLM 自己调用 activate_skill(技能名) 来激活，或用户说激活XX技能
动态工具加载：激活后技能的自定义工具自动注册到全局 TOOL_EXECUTORS，停用时自动卸载
知识注入：已激活技能的知识内容作为 system message 注入，无激活时不增加任何 token 消耗
重名保护：技能工具与核心工具重名时拒绝加载，防止冲突

新增 LLM 可调用工具（3个）：
list_skills — 列出所有可用技能及激活状态
activate_skill(name) — 激活指定技能，加载其工具和知识
deactivate_skill(name) — 停用指定技能

示例技能包：
skills/系统信息工具/ — 含自定义 get_system_info 工具（PowerShell 查询 CPU/内存/磁盘/网络），演示工具型技能
skills/学习助手/ — 纯知识注入（记忆曲线、费曼学习法、番茄工作法），演示知识型技能

12.16  记忆系统重构（2026-05-14）
修复了长期记忆系统的三个核心缺陷：

缺陷 1：记忆不再全量预加载到 System Prompt
之前 _build_system_prompt_once() 将 long_term.json 的 60+ 条全量注入 system prompt，token 消耗大且运行时新增记忆不可见。改为运行时按需检索：LLM 通过 search_memory 工具主动查询，不再被动全量加载。纯聊天路径不注入记忆说明，无额外 token 成本。

缺陷 2：新增 search_memory 运行时检索工具
LLM 可在对话中调用 search_memory(关键词) 搜索 long_term.json，返回所有匹配事实。

缺陷 3：新增 update_memory 和 delete_memory 工具
update_memory(old_keyword, new_fact) — 搜索匹配旧事实并替换。找不到则追加为新事实。
delete_memory(keyword) — 搜索并删除所有匹配的事实（不可恢复）。

记忆工具完整闭环：save_memory → search_memory → update_memory → delete_memory

自动日期标记：save_memory 和 update_memory 自动在事实末尾追加【记录于YYYY-MM-DD】，方便 LLM 判断记忆时效性。

针对 LLM 依赖启动时静态时间导致的时间不准、过时信息误答等问题，进行了四点优化：

实时时间注入：_function_calling_loop 每次调用时注入当前公历/农历/节假日信息，并提醒涉及时间节日先调 get_current_time。
时间问题强制路由：decision.py 新增时间/日期/节日类正则模式（现在几点、三月三、端午节等），确保这些不走纯聊模式。

         │
         ▼
  AgentCore.chat()          ← brain/agent.py
    │  parse_emotion_tag()  剥离标签 → 得到 emotion
    │  若未输出标签 → infer_emotion_from_text() 关键词推断
    │  返回干净文本（不含标签）

         │
         ├── 桌面端 ────────────────── gui/main_window.py
         │   _continue_response()
         │     → getattr(agent, '_last_emotion')
         │     → get_random_emotion_image(emotion) 概率触发
         │     → chat_widget.add_ai_image(path)
         │       → ImageMessageBubble (QMovie/QPixmap)
         │
         └── QQ 端 ────────────────── workers/qq_bridge_worker.py
             _parse_qq_emotion()
               → getattr(agent, '_last_emotion')
               → get_random_emotion_image(emotion) 概率触发
               → 存 _pending_emotion_img
             _send_qq_emotion_image()
               → 通过 OneBot API 发 file:// 图片消息
  核心逻辑
  1. 标签解析 — parse_emotion_tag()
  - 正则匹配 【表情：XXX】（兼容半角 []、［］、冒号后空格）
  - 从文本中移除标签，返回 (干净文本, 情绪词)
  - 二次兜底：re.sub 移除所有残留类标签模式
  2. 情绪推断 — infer_emotion_from_text()
  - LLM 未输出标签时的 fallback
  - 按优先级关键词匹配：道歉 > 工具调用 > 夸奖害羞 > 得意 > 思考 > 好奇 > 开玩笑 > 伤心 > 生气 > 开心 > 默认
  - 确保任何回复都能推断出一个情绪，不会漏
  3. 图片选取 — get_random_emotion_image()
  - 根据情绪标签查 EMOTION_FOLDER_MAP 获取文件夹名
  - 扫描文件夹内 jpg/png/gif 文件，随机选一张
  - 文件夹不存在或无图片 → 降级到"默认"文件夹
  4. 概率控制
  - emotion_probability 全局设置（默认 0.6，范围 0~1）
  - 每次触发时 random.random() < prob 决定是否发送

  5. 历史强化
  - agent.history 存原始文本（含标签），让 LLM 在后续对话中看到自己的情绪标签，强化输出行为
  - 数据库存干净文本，供 GUI 展示
  效果
  - 桌面端：AI 回复后，概率弹出图片/动图气泡
  - QQ 端：文字回复后，跟随式发送图片消息（OneBot file://）

12.26  观察模式（Observation Mode）（2026-05-27 新增）

观察模式使莲心像一只好奇的小宠物——通过肩载摄像头持续观察周围环境，自主转头→拍照→分析→发送到QQ，循环往复。用户消息可打断当前循环，处理完后继续观察。

2026-05-27 更新：移除了垂直舵机（观察模式不再使用垂直转向），复位位置改为水平90°竖直45°。

一、核心参数
	• 水平舵机范围：20~150°（PAN_MIN/PAN_MAX），避免撞击机械限位
	• 垂直舵机：观察模式不使用垂直舵机（仅 idel 期间维持当前角度）
	• 观察频率：每分钟最多 2 轮完整观察（CycleRateLimiter）
	• 空闲行为：频率受限时随机水平转头（不拍照），模拟左顾右盼
	• 图片压缩：JPEG 质量递减至 ≤200KB
	• 消息长度：LLM 生成 ≤300 字的拟人化描述
	• QQ 限速：每分钟最多 2 张图片（独立于循环限速）
	• 费用上限：每日视觉 API 费用 ¥5，超出自动退出（CostTracker）
	• 闲置超时：30 分钟无用户消息自动退出
	• 每轮转头：随机 1~8 次，步长 ±15~50°
	• 预热机制：每轮拍照先拍一张丢弃（清空 ESP32 帧缓冲），0.3s 后再拍正式照片，避免拿到旧帧

二、完整循环流程
	① 好奇转头（随机 1~8 次，20~150° 范围内，不使用垂直舵机）
	② 拍照（预热丢弃 + 正式，两连拍确保帧缓冲刷新）
	③ JPEG 压缩至 ≤200KB
	④ 检查当日费用是否超限
	⑤ SiliconFlow 视觉 API 分析图片内容
	⑥ LLM（DeepSeek）生成 ≤300 字拟人化描述，语气活泼好奇，称呼用户为"雨心"
	⑦ 发送图片 + 文字到 QQ（带 1~3 秒打字延迟）
	⑧ 检查 ESP32 健康状态（free_heap < 20KB 时退出）
	⑨ 登记本轮完成（CycleRateLimiter）

	连续失败保护：拍照/转头连续 3 次失败自动退出观察模式并发送 QQ 通知，防止无限重试。失败阈值包含照片、舵机控制和健康检查，每轮成功后重置计数。

莲心的QQ聊天功能
分段标记：
14.1  功能概述
莲心AI 通过接入 NapCatQQ 实现了 QQ 聊天功能。NapCatQQ 是一款基于 QQ NT 内核的 Shell 注入工具，它劫持 QQ NT 进程并向外暴露 OneBot v11 协议的 WebSocket 接口，使得莲心可以收发 QQ 消息并实时响应。
本功能使得莲心具备以下 QQ 对话能力：
私聊自动回复：任何用户发来的私聊消息均会触发回复
群聊 @ 回复：仅在用户 @ 机器人时触发回复，并自动 @ 发送者
多会话隔离：每个用户的私聊和群聊均拥有独立的 AgentCore 对话历史
记忆共享：所有 QQ 会话共享 long_term.json 记忆文件，与桌面版读写同一份长期记忆
14.2  技术架构
QQ 聊天功能的整体架构如下：
QQ 手机端 ←→ NapCatQQ（管理员窗口）── WebSocket ──→ QQBridgeWorker ──→ AgentCore（每用户独立实例）
                              端口 3001                workers/qq_bridge_worker.py
数据流说明：
NapCatQQ 作为 Shell 层注入 QQ NT 进程，劫持消息收发
NapCatQQ 在本地 127.0.0.1:3001 开放 WebSocket 服务器（OneBot v11 协议）
莲心端的 QQBridgeWorker（QThread 子线程）通过 WebSocket 客户端连接 NapCatQQ
QQBridgeWorker 接收消息后，提取文本并路由到对应会话的 AgentCore.chat() 方法
AgentCore 调用 DeepSeek API 生成回复，QQBridgeWorker 通过 OneBot API 将回复发回 NapCatQQ
NapCatQQ 将回复注入 QQ NT 进程，发送到对应的 QQ 好友或群聊
会话隔离策略：
私聊会话 key：qq_private_{user_id}
群聊会话 key：qq_group_{group_id}_{user_id}
每个 key 对应一个独立的 AgentCore 实例，拥有独立的短期对话历史
所有 AgentCore 实例共享同一个长期记忆（long_term.json）

群聊回复：仅在消息中包含 @机器人 时回复，并自动在回复中 @ 原发送者
会话隔离：私聊和群聊分别以不同 key 隔离，每个会话拥有独立的 AgentCore 实例和对话历史
长期记忆共享：所有 QQ 会话的 long_term.json 与桌面版共享，同一份记忆文件
自我消息过滤：忽略 QQ 号为机器人自身的消息，避免自回复循环
14.8  风控防护
为降低 QQ 账号被封禁的风险，实现了多层风控防护机制。以下机制在 workers/qq_bridge_worker.py 中实现：
（1）消息限速
同一会话每 4 秒最多回复 1 条消息。消息频率超过限制时自动忽略，并在日志中记录（限速前 3 次打印警告，之后静默）。
MIN_REPLY_INTERVAL = 3.0   # 同一会话最小回复间隔（秒）
（2）思考 + 内容相关打字延迟
收到消息后，先统一等待 8~15 秒模拟「思考」时间（AI 调用耗时另算）。思考完毕后，根据回复内容的字符数动态计算打字耗时：
THINK_DELAY = (3.0, 5.0)     # 思考延迟（秒）
TYPE_SPEED  = (65, 90)      # 打字速度（字/分钟）
例如，一句 10 字的回复约需 7~9 秒输入，一段 80 字的回复约需 53~74 秒输入。连续发送失败时延迟加倍（最多 4 倍），降低被行为分析检测到的概率。
（3）每日回复上限（按用户隔离）
每日回复上限按 QQ 用户隔离，不同用户拥有独立的计数器：主人（莲心主人，QQ 号 2648025746）每天最多回复 120 条，其他用户每天最多回复 30 条。跨日自动重置所有计数。
DAILY_LIMIT_OWNER = 120  # 主人每日上限
DAILY_LIMIT_OTHER = 30   # 其他用户每日上限
暗号机制：仅主人可发送暗号「解除限制」重置自己的当日计数（其他人回复「抱歉，你没有权限」）。达到上限时首次回复提醒消息（不计入计数），后续消息直接忽略。
（4）深夜静默机制
凌晨 1:00 至 7:00 为静默时段，默认不回复任何消息。但设计了暗号唤醒机制：
暗号"醒醒"：将机器人从静默中唤醒，之后正常回复
暗号"晚安好梦"：让机器人继续静默
白天天亮后自动退出静默状态
SILENT_HOUR_START = 1  # 凌晨静默开始（1:00）
SILENT_HOUR_END   = 7  # 凌晨静默结束（7:00）
（5）失败退避
连续发送消息失败时，发送延迟会根据连续失败次数逐步加倍（最多 4 倍），并在日志记录连续失败次数。
（6）可中断休眠
所有等待延迟以 0.5 秒为粒度循环检查 _running 标志，确保 stop() 方法可以快速中断休眠，避免退出时卡死。
（7）全局限速（多用户并发防护，2026-05-01 新增）
当多个 QQ 用户同时与莲心聊天时，即使每个会话各自有独立限速，莲心仍可能在短时间内连续发出多条消息。为防止被风控系统通过发送频率识别为机器人，增加了全局发送间隔：每次发送消息前检查距上次发送的时间，如果不足随机 8~15 秒，则额外等待至满足间隔。
GLOBAL_SEND_INTERVAL = (5.0, 10.0)  # 全局限速随机范围

（1）AgentCore 改造
AgentCore.__init__ 新增两个可选参数：

        self.history = [...]
        self._session_titled = True
    ...
    if user_desc:

（2）QQ 会话映射
QQBridgeWorker 内部维护 _session_map 字典（持久化到 memory/qq_session_map.json），将 QQ 会话 key 映射到数据库 session_id：

群聊 key：qq_group_{group_id}_{user_id} → DB session_id

未找到 → 创建新 AgentCore（自动生成新 DB session），保存映射到 JSON
重启后映射自动恢复，各用户回到各自独立的对话上下文

每个 QQ 用户拥有独立的数据库 session，对话历史互不干扰
长期记忆（long_term.json）仍全局共享，桌面版和 QQ 版读写同一份

14.16  智能分段发送（2026-05-01 新增）
当莲心的回复内容较长（超过 100~150 字随机阈值）时，系统会自动将其拆分为多条短消息，逐段发送以模拟真实人类的打字—停顿—继续打字节奏。
分段策略：优先按语义边界切分（段落 → 句号/问号/感叹号 → 逗号/分号 → 强制均分），每段长度在阈值范围内随机。
分段标记：非最后一段末尾自动添加「.. 」，表示话还没说完；最后一段无标记。接收方看到「..」就知道后面还有，没有则表示发送完毕。
中断机制：莲心在后台线程逐段发送消息，每段发送前会检查队列是否已被清空（新消息到达时主线程会清空并替换队列）。如果用户中途发来新消息，剩余未发的分段自动丢弃，莲心立即处理新消息。已发出的带「..」段落停留在原地，形成自然的话说一半被打断效果。
群聊优化：分段发送时仅第一段 @ 发送者，后续段落纯文本，避免群聊中反复提醒。
打字时间与内容挂钩：每段发送前按字符数计算模拟打字时间（45~90 字/分钟），字数越多等待越长。例如一段 100 字的段落需要 67~133 秒的打字时间，之后再间隔 5~10 秒才发下一条。
协作关系：段间间隔与全局限速（每 5~10 秒）协同工作，取较大值执行，确保任意两条消息之间都有足够的间隔。

【关于莲心说收不到用户的语音问题排查】
  QQ 语音消息接收失败 修复记录（2026-05-16）
问题现象：
莲心 QQ 桥接无法接收、转录用户发送的语音消息。日志显示 [语音] URL 下载失败: 本地路径 -> No connection adapters 或 [语音] url 非本地文件或已被清理，最终 AI 回复中显示
  [一段语音（下载失败）]。
根因
  NapCatQQ 的语音消息 url 字段是本地 AMR 文件路径（如 E:\Tencent\Tencent File\Tencent Files\<QQ>\nt_qq\nt_data\Ptt\<年>-<月>\Ori\<hash>.amr），而非 HTTP 链接。旧代码用 requests.get(url)
  处理它，requests 不支持本地路径。
  此外还有两个次要问题：
  1. NapCatQQ 可能返回 file:///E:/path/... 带前缀的路径，Python Path() 不识别
  2. QQ NT 边写语音文件边发 WebSocket，莲心读取时文件可能尚未落盘
  修改文件：
  workers/qq_bridge_worker.py 中的 _download_voice() 方法。

  修复内容：
  ① 本地文件路径检测（核心修复）
  _download_voice() 中新增方式 2：检测 url 是否为本地文件路径（不判断是否 HTTP），若是则用 shutil.copy2() 复制到临时目录返回。原有方式 1（file_id → get_file API）和方式 3（HTTP下载）保持不变。
  ② file:// 前缀兼容
用已有的 _resolve_file_path() 统一预处理 url 字段，将 file:///、file://、混合斜杠等格式转为 Windows 标准路径后，再调用 Path().is_file()。
③ 文件落盘重试
本地路径检测不命中时，不立即放弃，而是三级重试（等 0.5s → 1s → 2s，共 3.5 秒），应对 QQ NT 异步写文件的时序问题。
  ④ 日志限频绕过
  _process_voice() 开头加 time.sleep(0.15)，让 [语音] 前缀的日志避开 _log() 的 100ms 限频窗口，确保诊断信息可见。
  经验总结：
  - NapCatQQ 同一字段（url）在不同版本/配置下可能是 HTTP 链接、file:// 路径或裸本地路径，必须三种情况都兼容
  - OneBot v11 标准中语音消息的 file_id 字段经常为空，不能依赖，需优先处理 url 兜底
  - QQ NT 的语音文件存储在 Ptt/<年>-<月>/Ori/<hash>.amr，异步写入，读取需等待（500ms~2s）
  - _log() 的 100ms 刷屏限频会吞掉紧挨着 [收到] 日志的 [语音] 日志，排查时需留意

14.20  SQLite WAL 模式优化（2026-05-01 新增）
修复了 QQ 桥接使用过程中桌面 UI 偶发性卡死变白的 bug。
根因：桌面端和 QQ 桥接的 AgentCore 各自独立连接同一个 conversations.db 文件。QQ 后台线程写入对话历史时，SQLite 默认 journal 模式的写锁会阻塞主线程的读操作，导致 Qt 事件循环被短暂冻结（Windows 检测到窗口无响应后显示毛玻璃效果）。
修复：在 HistoryManager._init_db() 中执行 PRAGMA journal_mode=WAL（WAL 模式下读写不互斥）和 PRAGMA busy_timeout=3000（写冲突时最多等 3 秒而非立刻失败）。启用 WAL 后，QQ 后台线程写数据库时主线程读操作完全不受影响。

  架构设计
  采用三层回退策略处理合并转发消息：
  收到转发消息
      ├── 方式1: get_forward_msg API（NapCatQQ OneBot）
      │   └── 成功 → 逐节点处理（图片 Vision、文件提取、语音 Whisper、嵌套递归）
      └── 方式1 失败 → 方式2: XML 回退解析
          └── 从消息段原始 XML 预览提取文字摘要

  - MAX_FORWARD_NODES = 100 — 单次处理最多 100 条消息
  - MAX_FORWARD_CHARS = 4000 — 输出上限 4000 字符
  - MAX_FORWARD_DEPTH = 2 — 嵌套转发最大递归 2 层
  新增方法
  1. _extract_forwards(msg_data) — 从 OneBot 消息段中识别 type: "forward" 的段，提取转发 ID 并保留完整 data 供回退使用。
  2. _process_forward(forward_urls, text, session_key) — 入口方法，重置图片计数器，遍历转发 URL 列表调用 _get_forward_content，将展开后的聊天记录与用户文字合并。
  3. _get_forward_content(forward_id, depth, session_key, raw_data) — 调用 get_forward_msg API 获取转发详情；统计参与者、发言人数；逐条调用 _format_node 格式化；长度超限自动截断；API
  失败时降级到 XML 回退。
  4. _format_node(node, depth, session_key) — 格式化单条消息节点：
  - 解析发送者（nick + QQ 号）和时间戳
  - 遍历消息段（text/image/file/voice/video/forward 等）
  - text：直接拼接
  - image：调用 _describe_forward_image → 下载图片 → SiliconFlow Vision API 描述（上限 10 张/轮）
  - file：调用 _read_forward_file → file_id 解析或本地路径查找 → _extract_full_text 提取（上限 3000 字）
  - voice：调用 _transcribe_forward_voice → 下载语音 → Whisper 转录
  - forward（嵌套）：递归调用 _get_forward_content(depth+1)，缩进展示
  - 未知类型：尝试 text/content/data/title 字段，否则显示 [类型名]
  5. _parse_forward_xml_fallback(raw_data, depth, session_key) — API 崩溃时的降级方案：解析 QQ 协议 XML 预览（<source> 来源名、tSum 总条数、<title> 逐条消息文字摘要），输出文字大纲。

  - _process_merged_segments()（第 1253 行）：分段消息也支持转发

  - 图片计数隔离：self._forward_img_count 每轮转发重置，避免多次转发互相影响

【肩载设备】
莲心AI 肩载设备开发档案
最后更新：2026-05-25

1. 项目概述
莲心AI肩载设备是为莲心AI桌面助手开发的肩部挂载硬件外设，通过WiFi与莲心AI通信，支持远程拍照、舵机云台控制、温湿度监测、OLED调试显示等功能。采用WebSocket云中继方案，ESP32-CAM可在手机热点网络下与家中PC远程通信。
2. 通信架构
当前采用三段式通信架构：
QQ → 莲心 AI(PC) → Render云中继(WSS:443) → ESP32-CAM(手机热点)
云中继地址：https://shoulder-relay.onrender.com
中继保活：UptimeRobot 每 5 分钟 HTTP GET
局域网直连：ESP32 的 HTTP MJPEG 推流 (端口 80) 仅在局域网可用

5. 供电方案
电源拓扑：
7V 蓄电池 → MP1584 (降压至5.3V) → 5V 总线
5V 总线 → ESP32-CAM 5V pin + 舵机 VCC + OLED VCC
ESP32-CAM 板载 3.3V 稳压 → DHT11 VCC
所有模块共地（电池负极 → MP1584 IN- → OUT- → 各模块 GND）

注意：MP1584 输出电压需调到 5.3V 左右补偿线损和舵机启动瞬态压降。两个SG90同时堵转电流可达1.5A，5V走线需要加粗。

8. 注意事项
GPIO1 是 UART TX，用作 I2C SDA 后会失去串口输出功能；调试时可临时断开 OLED SDA 恢复串口
GPIO12 是 strapping 引脚，接上拉电阻会导致 ESP32 启动时进入错误的 flash 电压模式，应避免使用
GPIO16 被 PSRAM 占用，不能用作普通 GPIO
烧录时需手动 FLASH+RST（因 GPIO12 空闲无上拉，auto-reset 可能失效）
两个 SG90 同时转动可能导致 5V 总线瞬间压降，MP1584 输出端建议加 1000μF 电解电容
Render 免费版 15 分钟无活动会休眠，需要 UptimeRobot 保活
MQTT (broker.emqx.io) 在中国手机运营商网络下端口被封（1883/8883），故改用 WebSocket 中继方案
