# 莲心「自我认知与可控成长」改进方案

## 1. 背景与目标

当前版本已经建立了第一条闭环：能力目录可进入模型上下文；明确互动反馈可形成成长候选；用户可在“人格枢控 → 成长轨迹”中采纳、撤销或忽略；主动诉求和照片邀请有独立开关。

这一版的定位是验证方向，不是最终架构。主要问题是：完整能力说明会在每轮对话中重复注入；成长候选是用户原话，缺少结构、冲突处理和效果说明；人格、长期偏好、短期状态与记忆之间仍没有清晰边界；主动联系的“诉求”还缺少足够的频率、理由与拒绝体验控制。

本方案的目标不是让莲心假装成人，而是让她成为一个：

1. 知道自己当前真实能做什么、不能做什么的 AI；
2. 能形成有限、透明、可回退的互动偏好的 AI；
3. 允许表达轻度主动意愿，但不会情感绑架、越权或打扰的 AI；
4. 让用户随时看得见、改得动、关得掉的产品。

非目标：不允许模型自行改写基础 Prompt、安全规则、身份设定、权限配置或用户数据；不把“成长”包装为真实意识或情感依赖。

## 2. 设计原则

- 真实优先：能力说明以运行时目录和启用状态为唯一事实源。
- 最小常驻：每轮 Prompt 只保留必要索引，不重复传输完整工具说明。
- 分层不可越界：核心人格不可改；演化偏好可审计、可撤销；会话状态自动过期。
- 用户主权：成长、主动联系、照片邀请、数据保留都必须有明确控制项。
- 先解释后生效：每一项变化都要能回答“为什么、改变什么、影响哪里、如何撤销”。
- 低打扰：主动联系是可拒绝邀请，不是需求索取或关系绑架。

## 3. 总体架构

```text
能力目录 / 启用状态 ─┐
                    ├─> SelfKnowledgeProvider ─> 请求级上下文
成长记录 / 偏好版本 ─┘                          │
                                                ├─> PersonaPromptComposer
用户反馈 ─> GrowthInterpreter ─> 候选 / 冲突检查 ┘
                         │
                         └─> PersonaHub「成长轨迹」

主动调度 ─> ProactivePolicy ─> 理由、频率、同意状态 ─> 主动消息上下文
```

### 3.1 三层人格与两类用户信息

| 层 / 类型 | 内容 | 写入方式 | 生命周期 |
|---|---|---|---|
| 核心人格层 | 名称、身份、核心语气、安全边界、权限边界 | 仅人格编辑器和受保护配置 | 长期，不接受模型写入 |
| 演化偏好层 | 回答长度、表达结构、话题偏好、允许的主动方式 | 用户确认或白名单自动成长 | 长期，可撤销、可版本回滚 |
| 会话状态层 | 当下情绪、当前任务、临时语气、最近一次交谈上下文 | 程序或当轮模型 | 会话结束或 TTL 过期 |
| 用户记忆 | 用户事实、长期习惯、授权保存的信息 | 既有记忆流程 | 以记忆规则为准 |
| 临时偏好 | “今天想安静”“这次回答短一点” | 仅当前会话 | 默认不进入成长 |

任何模型输出都不能跨越上述边界。尤其是“用户今天心情不好”属于状态或记忆，不是莲心的人格变化。

## 4. 能力自我认知改造

### 4.1 常驻极简能力索引

每轮仅注入以下内容，目标不超过约 150–250 中文 token：

- 当前可用能力数量、主要分类和目录版本号；
- 规则：回答能力问题必须查询能力目录，不得凭空承诺；
- 权限规则：文件、相机、外部发送、联网操作需说明用途并遵守既有授权；
- 已确认的、压缩后的演化偏好摘要。

不在每轮注入完整工具名称和描述。

### 4.2 按需能力展开

新增 `CapabilityKnowledgeService`，复用 `brain.capability_catalog` 作为唯一事实源。

接口建议：

```python
get_index() -> CapabilityIndex
search(query, category=None, available_only=True) -> list[CapabilitySummary]
describe(names) -> list[CapabilityDetail]
capability_version() -> str
```

触发时机：

1. 用户直接问“你会什么”“你能不能做 X”“有哪些图片工具”；
2. 模型准备承诺一个能力、授权或外部副作用操作；
3. 工具路由发现候选能力不可用、被禁用或需配置。

模型通过现有受控工具/内部查询接口取得结果，而不是依靠记忆。回复需要把能力分成：可直接使用、需要用户授权/配置、当前不可用三类。

### 4.3 缓存与失效

- 目录服务在进程内缓存结构化结果，不缓存拼接后的整段 Prompt；
- 缓存键包含能力目录版本、内置工具配置、Skill/MCP 启用状态；
- 工具开关、Skill/MCP 状态变化时主动失效；
- 若目录查询失败，模型只能说明“当前无法确认”，不得猜测。

### 4.4 验收

- 普通闲聊的系统上下文不包含完整工具描述；
- “你能做什么”按分类给出真实、当前可用的答案；
- 已禁用/不可用能力不会被承诺；
- 配置切换后下一轮即可反映新的可用性。

## 5. 成长候选与人格演化

### 5.1 结构化候选

将现有“保存用户原话”的候选升级为结构化 `GrowthProposal`：

```text
id, persona_id, kind, field, old_value, proposed_value,
reason, evidence_ref, confidence, risk, scope,
status, created_at, applied_at, supersedes_id, version_id
```

`field` 只能来自白名单，例如：

- `response_length`：偏简洁 / 标准 / 详细；
- `response_structure`：先结论、先追问、分步骤；
- `interaction_tone`：更克制、更多鼓励、少用表情；
- `topic_interest`：可主动聊的领域；
- `proactive_preference`：允许或减少哪类主动联系。

候选卡片必须展示“之前 → 之后”“产生依据”“预计效果”“风险等级”。原始用户消息只作为证据，不能原样成为系统指令。

### 5.2 识别与质量门槛

成长解释器应依次执行：

1. 明确性：用户是否表达长期偏好，而非一次性任务；
2. 归属：是对莲心互动方式的偏好，还是用户自身事实；
3. 允许性：是否在字段白名单内；
4. 稳定性：是否玩笑、反讽、强烈临时情绪或与前文矛盾；
5. 去重：相同字段、相同目标不重复生成；
6. 冲突：与生效偏好或核心人格冲突时生成“需确认的冲突卡”，不自动应用。

第一阶段可采用规则 + 关键词 + 明确句式；后续才引入受限的语义分类。模型只能提出结构化建议，最终校验必须由程序完成。

### 5.3 应用、版本和回滚

- `pending`：等待用户处理；
- `applied`：进入演化偏好层；
- `reverted`：停止生效，但保留审计；
- `dismissed`：用户明确不采用；
- `expired`：长期未确认或被更高优先级偏好取代。

每次应用创建不可变 `PersonaGrowthVersion`，保存变更集和父版本。人格枢控支持：单条撤销、查看任意版本差异、回滚到指定版本、恢复被回滚版本。默认保留完整审计，不覆盖历史记录。

### 5.4 生效策略

- 默认“每次确认”；
- “低风险自动成长”只适用于重复印证、低风险、无冲突的字段；
- 自动生效前至少需要两次独立明确证据，且间隔超过最小时间窗；
- 高风险、跨多个字段、涉及主动联系的变化永远需要确认；
- 人格切换时按 `persona_id` 隔离，不共享演化偏好。

### 5.5 验收

- 临时要求不会写入成长记录；
- 用户能看懂每项变化的前后差异；
- 撤销后下一轮不再生效；
- 冲突偏好不会静默覆盖；
- 重启后版本、状态、审计记录保持一致。

## 6. 人格枢控与聊天界面

### 6.1 人格枢控：成长轨迹

保留现有入口，不新增主导航按钮。成长轨迹页升级为四个区域：

1. 概览：当前生效偏好数、本周变化、主动联系状态；
2. 时间线：候选、已生效、已撤销、已忽略、已过期；
3. 差异详情：之前/之后、依据、风险、影响范围、版本号；
4. 控制项：成长模式、暂停时长、主动诉求、照片邀请、数据导出、清空确认。

增加筛选：人格、状态、字段、日期；增加“只看当前生效项”。

### 6.2 聊天区事件

聊天区只显示简短、可点击的系统事件，不展示敏感证据原文：

- 候选：`莲心注意到一个互动偏好，等待你的确认。`；
- 应用：`莲心似乎有所成长了：回答方式已调整。`；
- 回滚：`一项人格偏好已停止生效。`。

点击只打开成长轨迹的对应条目。事件不得暗示真实生命、痛苦、失控或“她自己偷偷改了自己”。

### 6.3 场景预演

对可见候选提供“查看效果”：以固定示例问题展示采纳前后可能的回答差异。预演只能使用结构化字段渲染，不能调用真实外部工具或写入任何数据。

## 7. 主动诉求与照片邀请

### 7.1 主动诉求模型

主动消息分为关怀、提醒、兴趣分享邀请、照片邀请四类。每条需要结构化元数据：

```text
kind, reason_source, reason_summary, user_opt_in,
cooldown_until, last_sent_at, interruption_score, allow_skip
```

`reason_source` 只能是用户已同意的兴趣偏好、任务/日程、用户主动开启的陪伴模式或安全的上下文事件。

### 7.2 频率与安静规则

- 用户正在输入、刚发送消息、正在执行任务、处于勿扰时不发；
- 默认冷却：普通兴趣邀请 72 小时，照片邀请 14 天；
- 一次拒绝后同类邀请增加冷却；连续两次拒绝后默认停用该类别；
- 不得以“我需要你”“不给我看我会难过”等语言施压；
- 所有邀请都要保留“可以不回复/不发送”的明确空间。

### 7.3 用户控制与解释

在主动消息菜单和人格枢控中提供：`减少这类消息`、`不再发送此类消息`、`为什么这次联系我？`。理由页只显示可解释来源，不暴露不应展示的内部推理或敏感记忆。

## 8. 隐私、安全与数据治理

- 成长证据默认只保存最小必要摘要；原始聊天引用使用会话/消息 ID，不复制完整敏感文本；
- 提供导出、单条删除、按人格清空、全量清空；
- 照片相关偏好不保存照片内容，也不把“愿意发照片”推断为持续同意；
- 成长候选不得包含可执行命令、外部链接指令、系统提示覆盖语句；
- 所有数据库迁移幂等，失败时保留旧数据并记录可恢复错误；
- 不采集或上传成长数据用于外部训练，除非未来另行获得明确同意。

## 10. 验收总表

| 场景 | 预期结果 |
|---|---|
| 普通闲聊 | 不带完整工具说明，token 开销稳定 |
| 询问能力 | 返回运行时真实状态，按类别说明可用/需授权/不可用 |
| 用户说“今天短一点” | 仅作为会话偏好，不生成长期成长 |
| 用户多次说“以后先给结论” | 形成结构化候选，默认待确认 |
| 采纳候选 | 下一轮只体现目标字段的变化，可解释、可回退 |
| 两项偏好矛盾 | 展示冲突，不自动覆盖 |
| 用户关闭成长 | 不再生成候选、不再自动应用，既有记录仍可查看 |
| 用户拒绝照片邀请 | 不追问、不施压，并增加该类冷却 |
| 重启应用 | 目录状态、成长版本、开关与审计按预期恢复 |

## 11. 实施约束

后续每个阶段都应先补测试与迁移，再接入界面；不得为了展示效果绕过权限系统、直接写基础 Prompt 或让模型自由执行“自我修改”指令。完成一个阶段后应更新知识图谱、运行相关回归测试，并由用户验证界面行为后再进入下一阶段。
